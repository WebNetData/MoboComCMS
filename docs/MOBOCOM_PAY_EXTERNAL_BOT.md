# اتصال ربات پذیرنده به موبوکام‌پی

این راهنما برای ربات یک پذیرندهٔ دیگر است. مشتری در موبوکام‌پی پرداخت می‌کند و
موبوکام نتیجه را به API پنل همان پذیرنده می‌فرستد. ارتباط با BotFather یا توکن
ربات تلگرام لازم نیست. ساخت فاکتور و تأیید سفارش از طریق HTTPS انجام می‌شوند.

## تنظیم دو طرف اتصال

در موبوکام‌پی، پذیرندهٔ فعال یک پایانه با نوع «ربات» می‌سازد و از بخش اتصال
درگاه به ربات، این موارد را ثبت می‌کند:

1. نشانی تأیید پنل خودش، مثلاً `https://bot.webnetdata.ir/api/payment`.
2. کلید API همان پنل با دسترسی «پرداخت»، در فیلد کلید تأیید. این کلید با کلید
   ساخت فاکتور موبوکام فرق دارد و روی سرور رمزگذاری می‌شود.
3. معیار پاسخ موفقی که مستندات یا آزمون واقعی پنل تأیید کرده‌اند. برای
   `{"status":true}` گزینهٔ همین پاسخ، برای `{"ok":true}` گزینهٔ مربوط به آن و
   برای `{"status":"success"}` گزینهٔ متن موفق را انتخاب کنید. مقدار `"true"`
   رشته‌ای، پاسخ موفق boolean نیست. پاسخ منفی بر سایر فیلدهای مثبت اولویت دارد.

گزینهٔ HTTP موفق فقط وقتی مناسب است که قرارداد پنل صریحاً موفقیت هر پاسخ ۲xx
را تضمین کند. از روی پاسخ «توکن نامعتبر» نمی‌توان قالب موفقیت را تعیین کرد.
تا انتخاب معیار، اتصال فعال نمی‌شود. تغییر تنظیم اتصال، تحویل سفارش‌های قبلی
را برای بازبینی متوقف می‌کند؛ تنظیمات را وسط پرداخت‌های باز بی‌دلیل تغییر ندهید.

پس از ذخیره، موبوکام نشانی ساخت فاکتور و یک کلید جدید نشان می‌دهد. این دو را
در پنل ربات، بخش «مالی ← تنظیمات درگاه سفارشی» قرار دهید:

| محل در پنل ربات | مقدار |
| --- | --- |
| آدرس API | نشانی نمایش‌داده‌شدهٔ `https://YOUR-MOBOCOM-DOMAIN/api/v1/pay/bot/INTEGRATION_ID` |
| توکن API | کلید ساخت فاکتور صادرشده توسط موبوکام با پیشوند `mcpbot_` |

کلید ساخت فقط یک بار نمایش داده می‌شود. اگر آن را ندارید، از تغییر کلید استفاده
و مقدار جدید را در ربات جایگزین کنید. کلیدها را در URL، چت یا مخزن کد قرار ندهید.

## قرارداد ساخت و تأیید

ربات به نشانی ساخت فاکتور درخواست POST با `Content-Type: application/json`
می‌فرستد. پنج فیلد `api_key`، `amount`، `order_id`، `user_id` و `type`
لازم‌اند. مبلغ به **تومان** است و موبوکام آن را به ریال تبدیل می‌کند. این نمونه
از شکل رشته‌ای که پنل‌های ربات می‌فرستند استفاده می‌کند.

```json
{
  "api_key": "MOBOCOM_CREATION_KEY",
  "amount": "10000",
  "order_id": "unique-order-123",
  "user_id": "123456789",
  "username": "example_username",
  "first_name": "علی",
  "type": "purchase",
  "payment_count": "3",
  "register": "1735689600",
  "membership_days": "45",
  "balance": "25000"
}
```

`amount` و `user_id` عدد صحیح مثبت یا رشتهٔ رقم‌های لاتین می‌پذیرند. مبلغی مثل
`"10000"` با `10000` برابر است. برای رشته از رقم لاتین، بدون جداکننده و بدون
صفر پیشرو استفاده کنید. `type` یکی از `purchase`، `renewal` و `balance_increase` است.

فیلدهای اختیاری `payment_count`، `register`، `membership_days` و `balance` نیز
عدد صحیح یا رشتهٔ عدد صحیح می‌پذیرند. حذف فیلد، `null` و `""` همگی یعنی مقدار
ارسال نشده است. تعداد پرداخت و روزهای عضویت فقط برای قواعد مسیر استفاده می‌شوند؛
`-1` برای عضویت مجاز است و شرط حداقل مثبت را برآورده نمی‌کند. اگر خطای ۴۲۲ نام
یک فیلد را نشان داد، مقدار همان فیلد را به‌شکل مستند بفرستید یا اگر اختیاری است
و مقداری برایش ندارید، آن را حذف کنید.

در تنظیم اتصال موبوکام‌پی، برای دکمهٔ شیشه‌ای گزینهٔ «فهرست دکمه‌ها (links)» را
در فیلد «پاسخ ساخت لینک» انتخاب کنید. پاسخ، آرایه‌ای از دکمه‌هاست که ربات باید
با `text` و `url` زیر پیام پرداخت نمایش دهد. بدون قانون مسیریابی، یک دکمه با عنوان
«پرداخت امن با موبوکام» برمی‌گردد. با یک قانون منطبق، هر روش مجاز دکمهٔ خودش را دارد.

```json
{"links":[{"text":"پرداخت امن با موبوکام","url":"https://YOUR-MOBOCOM-DOMAIN/pay/PAYMENT_ID"}]}
```

اگر ربات تنها پاسخ تک‌لینک را پشتیبانی می‌کند، حالت `url` را انتخاب کنید و همان
نشانی را در دکمهٔ پرداخت ربات قرار دهید. خطا بدنهٔ JSON با `ok:false` و `message` دارد.
تکرار همان سفارش با همان اطلاعات، فاکتور تازه و اعتبار دوباره نمی‌سازد. برای
جایگزینی فاکتور منقضی، ربات باید شناسهٔ سفارش جدید صادر کند.

| کد | بررسی در سرور ربات یا پنل |
| --- | --- |
| ۴۰۱ | کلید `mcpbot_` و شناسهٔ همان اتصال را با تنظیم پایانهٔ فعال تطبیق دهید. |
| ۴۰۹ | مبلغ، کاربر، نوع و شناسهٔ سفارش را با اولین درخواست مقایسه کنید. تا روشن شدن وضعیت سفارش، پرداخت دیگری برای آن نسازید. |
| ۴۲۲ | نام فیلد در پیام را بررسی کنید. مقدار فیلد اختیاریِ ناموجود را حذف کنید و مبلغ صحیح را به تومان بفرستید. |
| ۴۲۹ | کمی بعد همان سفارش را دوباره بفرستید. |
| ۵۰۳ | باز بودن دریافت، روش‌های مجاز پایانه و وضعیت نگهداری را بررسی کنید. در خطای موقت، همان سفارش را پیگیری کنید. |

پس از ثبت قطعی پرداخت، صف موجود موبوکام به پنل پذیرنده درخواست زیر را می‌فرستد:

```http
POST /api/payment
Token: MERCHANT_PANEL_PAYMENT_KEY
Content-Type: application/json
```

```json
{"order_id":"unique-order-123","actions":"custom_payment_verify"}
```

این دامنه و کلید متعلق به **پنل ربات پذیرنده** هستند. پاسخ موفق باید با معیار
انتخاب‌شده مطابق باشد. تحویل «نامشخص» به معنی ناموفق بودن پرداخت مشتری نیست:
ممکن است پنل سفارش را اعمال کرده و پاسخ در شبکه قطع شده باشد. موبوکام این حالت
را خودکار تکرار نمی‌کند. ابتدا وضعیت سفارش در پنل مقصد بررسی و سپس از مسیر
بازیابی صریح اقدام کنید. خطاهای قطعیِ پیش از ارسال POST تا پنج تلاش با فاصلهٔ
افزایشی بازیابی می‌شوند؛ شکست پروکسی باعث اتصال مستقیمِ پنهانی نمی‌شود.

## فعال‌سازی تأیید بانکی توسط مدیر

پذیرنده کارت‌های پلتفرم را مصرف می‌کند و کارمزد می‌دهد؛ تنظیم منبع بانکی، کلید
پیامک و مجوز تأیید خودکار در اختیار مدیریت است. در مدیریت، حساب مقصد
و درگاه کارت‌به‌کارت مربوط را تنظیم کنید، تأیید خودکار پیامک را روشن کنید
و مجوز پذیرنده و پایانه را جداگانه فعال کنید. صرف ساخت پایانه کافی نیست.

- برای پیامک، از [راهنمای SmsForwarder](MOBOCOM_PAY_SMS_FORWARDER.md) استفاده
  کنید. موبوکام URL اختصاصی، کد بانک و توکن تولید می‌کند. متد POST، بدنهٔ JSON و
  جای‌گذاری متن پیام به‌صورت `{msg}` لازم است. فیلتر فرستندهٔ بانکی، مجوزهای
  گوشی و جلوگیری از ارسال مجدد پیام‌های تاریخی را روی گوشی بررسی کنید.
نخستین تأیید معتبر که قفل تراکنش را به دست
می‌آورد، پرداخت را ثبت می‌کند. تأیید دستی و پیامک از همان ثبت مالی مشترک
استفاده می‌کنند؛ پیام دیرهنگام یا تأیید دوباره، اعتبار جدید ایجاد نمی‌کند.
اعتبار مشتری از مبلغ اصلی فاکتور است؛ کارمزد و مبلغ ریز تشخیص به آن اضافه
نمی‌شوند. سهم پذیرنده نیز طبق مبلغ خالص و نرخ ثبت‌شدهٔ سفارش محاسبه می‌شود.

برای اعلان واریز معتبر، ثبت اعلان و کار بازیابی در یک تراکنش انجام می‌شود.
تطبیق فوری همچنان اجرا می‌شود؛ اگر پردازش همان لحظه قطع شد، صف مشترک عملیات
می‌تواند آن را بازیابی کند. پردازشگر صف باید روی سرور فعال و سلامت آن بررسی شود.
زمان رسیدن اعلان و وضعیت شبکه روی سرعت واقعی اثر دارند.

**محدودیت پیامک ساده:** بدنهٔ سه‌فیلدی `sms`، `bank`، `token` به ارسال‌کنندهٔ
مجاز اعتماد دارد و به‌تنهایی زمان یا هویت فرستندهٔ بانکی را اثبات نمی‌کند. برای
خرید با نرخ قفل‌شدهٔ USDT، پیامک فاقد شاهد زمانی معتبر به تأیید خودکار تبدیل
نمی‌شود و نیازمند بررسی است. این کنترل را با تغییر الگوی متن دور نزنید.

## پروکسی اختیاری برای پنل پذیرنده

فیلتر بودن تلگرام لزوماً به معنی نیاز API پنل ربات به پروکسی نیست. در صورت نیاز،
از مدیریت «پنل سرور ← پروکسی Xray» یک پیکربندی موجود را برای کار
«تأیید پرداخت ربات پذیرندگان» انتخاب کنید. کاربرد «تلگرام» همچنان برای API خود
تلگرام است و جای این گزینه را نمی‌گیرد.

ابزار نصب‌شدهٔ Xray باید سازندهٔ نسخهٔ ۴ داشته باشد. مدیر سرور پس از به‌روزرسانی
کد می‌تواند با همان نصب‌کنندهٔ موجود آن را ارتقا دهد:

```sh
sudo bash /opt/mobocom/app/deploy/ubuntu/xray-install.sh
```

این فرمان برای نصب استاندارد در مسیر بالا است؛ مسیر نصب متفاوت را مطابق سرور
خودتان تنظیم کنید. سپس تنظیم مسیرها را ذخیره و اعمال کنید. ابزار قدیمی اجازهٔ
انتخاب کاربرد تازه را نمی‌دهد. ورودی اختصاصی فقط روی `127.0.0.1:10810` است؛ آن
را در فایروال عمومی باز نکنید. مقصد به IP عمومی و پورت ۴۴۳ محدود است و گواهی
TLS همچنان با نام اصلی پنل بررسی می‌شود. آزمون «تونل TLS وصل شد» هیچ سفارش
مالی ارسال نمی‌کند و اثبات پذیرش پرداخت توسط پنل نیست.

## پذیرش نهایی روی سرور

پس از نصب نسخه‌ای که این قرارداد را پشتیبانی می‌کند، یک سفارش آزمایشی بسازید.
نشانی و کلید ساخت را در ربات و کلید پرداخت پنل را در موبوکام وارد کنید. قالب
پاسخ موفق را با نتیجهٔ واقعی تأیید کنید. یک پرداخت بانکی آزمایشی باید دقیقاً یک
پرداخت قطعی، یک اعتبار خالص پذیرنده و یک فعال‌سازی سفارش در پنل مقصد بسازد.
سپس ارسال مجدد پیامک و اقدام دستی پس از تأیید را بررسی کنید. موجودی باید ثابت بماند.
قطع دریافت، مهلت فاکتور، رسید در حال بررسی و وضعیت نامشخص تحویل را نیز کنترل کنید.

آزمون عملیاتی شامل اتصال واقعی گوشی، مسیر شبکهٔ سرور و قرارداد موفقیت پنل پذیرنده است.
