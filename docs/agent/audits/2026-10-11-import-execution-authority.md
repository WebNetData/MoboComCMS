# Import execution authority — 2026-10-11

## Canonical implementation

The existing import engine, job/record history, adapters and operations queue remain. `Identity/server/access.ts::resolveCurrentUser` is extracted from `requireUser`; requests and queued human actions use the same current account/global-authentication/password/role facts. Import authority composes this owner, existing RBAC and existing staff two-factor policy with the existing `imports.manage` permission. No second identity, permission key, restriction store, queue, module UI or Admin setting is added.

Start/resume/explicit rollback capture the current authorized operator on ImportJob and claim the expected state/updatedAt. Upload creator/email and historical content/records remain immutable. Nullable actor/time preserve legacy jobs, whose creator/creation time is checked without an exemption. Continuation mode keeps paused rollback separate from import execution; an authorized different operator can repair a denied creator's import. Completion audits use the executing operator and retain creator in metadata.

Workers check current authority before prepare, each plan/write/rollback and completion. Authority-fact denial/unavailability pauses without consuming the next record or silently requeueing it. Forum-only restrictions remain independent. Existing password-reset clock tolerance and the canonical two-factor policy's short cache remain; this does not claim instantaneous policy invalidation. A transaction already started may finish. Total database outage cannot persist a pause while storage is unavailable; this slice does not invent a fail-open fallback.

Execution grants atomically increment a persisted generation. Command and worker continuation/state/progress/lease-release claims include it, so equal actor IDs and equal timestamps cannot let an old grant modify a newer grant. Explicit resume/rollback refuses with 409 while an acknowledged record lease is active; the record must finish first. This does not claim comprehensive distributed fencing of every pre-existing adapter callback or cancellation of an in-flight transaction.

## Migration and deployment

Additive migrations `20261220120000_import_execution_authority` and `20261221120000_import_execution_generation` are listed as unreleased in the existing manifest and both schemas. No applied migration was rewritten to add generation. Actor pairing/positive ID, RUN/ROLLBACK mode and nonnegative generation are database constraints. Legacy ROLLING_BACK jobs receive ROLLBACK mode; no creator, history, cursor, counter, date or standing is reset.

Actual new SQL is applied to empty and populated old-shaped relations inside disposable, rolled-back PostgreSQL schemas; every original column is compared. Ordinary old readers/writers remain schema-compatible. **Quiesce old import workers and state-changing import commands for rollout**, migrate/generate/deploy the matching binary, then reopen. Old binaries do not understand new grant fencing or paused rollback direction; do not claim mixed-worker semantic compatibility. No root :3000 rollout, production certification, push, PR, merge or hosted workflow is performed by this package.
