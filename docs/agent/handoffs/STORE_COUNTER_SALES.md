## Implementation and ownership

- `/admin/store/counter` and private `/api/admin/store/counter` require Store enabled and `orders.manage`; delivery specialists alone cannot record received money. The transaction rechecks current authorization. Existing proxy Origin protection applies.
- Store's `server/counter-sales.ts` facade composes existing Catalog inventory/code-pool owners and Billing invoices/payments. The same serializable transaction writes Order/OrderLine, Invoice, Payment, stock reservation/consumption, assigned encrypted codes, delivered ProductDelivery, sale counters/events and strict Audit. No parallel customer, checkout, payment or inventory service.
- Guest purchases retain `userId: null`, cashier identity and optional name/phone snapshots. Linking an active existing customer retains the canonical UserId. A counter invoice has no guest wallet credit. Historical orders/invoices default to ONLINE and keep their buyer. Both Prisma schemas and migration `20270311120000_store_counter_sales` are included in the unreleased manifest.
- Supported products are active own-store physical goods and virtual CODES products, with their active variants, normal server retail prices and existing validated/sealed order fields. Shipping, online promotions, open amounts, marketplace sellers and manual/service products are outside this counter command. Physical goods are handed over immediately. Cash/card records the cashier's explicit received-money confirmation and optional terminal reference; it does not operate a card terminal.
- Codes come from the selected product/variant pool. Existing online holds keep their entitlement; the counter refuses an empty code pool even where online STAFF fallback remains available. Finite stock is shared with the site; existing unlimited-stock and STAFF fallback policies remain intact. Printing only reads already assigned codes.
- UUID + actor + normalized payload fingerprint provides durable replay/conflict protection. Bounded retries handle Prisma serialization/deadlock/unique conflicts, including PostgreSQL raw-lock SQLSTATE40001. Ambiguous browser outcomes retain the same payload/key; a reload resolves the stored UUID before another sale. A retry refusal cannot establish that the original did not commit.
- The receipt reads persisted financial/line/customer values and reuses the current product card design. Code values are immediately static for printing and every receipt read is strictly audited. Print cancellation or a receipt read failure never submits another sale. Store order detail links back to the saved counter receipt and avoids fake guest account/ticket links; snapshot name/phone is searchable.
- Account-only fulfillment, wallet, subscription/referral/loyalty and marketing readers explicitly skip/reject guest-only actions. Billing's transaction-aware settlement defers its ordinary standalone post-commit notification/provider effects; counter sales intentionally use the in-person receipt and linked-account order/code views. No automatic SMS/email or external provider call was added.
