# دریافت نسخه و ارتقای سایت در حین توسعه

سورس در GitHub توسعه پیدا می‌کند؛ سایت نصب‌شده مستقل از شاخه‌های توسعه می‌ماند. هر وقت یک مجموعه تغییر تست و برای انتشار انتخاب شد، از یک commit مشخص بستهٔ امضاشده ساخته و در **[Releases موبوکام](https://github.com/WebNetData/MoboComCMS/releases)** بارگذاری می‌شود. لازم نیست پروژه به پایان برسد یا برای هر commit سایت را آپدیت کنید.

## مدیر سایت: فایل آپدیت را از کجا بگیرم؟

1. [صفحهٔ Releases](https://github.com/WebNetData/MoboComCMS/releases) را باز کنید. برای دریافت فایل، نیازی به نصب Git روی سرور نیست.
2. توضیح همان نسخه، وضعیت **Pre-release**، نسخهٔ فعلی سایت و نیازهای استقرار را بخوانید. نسخهٔ پایدار را برای سایت اصلی انتخاب کنید. پیش‌انتشار برای ارزیابی نسخهٔ مشخص پیش از اعلام پایداری است؛ به معنی تأیید استقرار روی سرور شما نیست.
3. از **Assets** فایل مناسب را دانلود کنید:

| فایل | کاربرد |
| --- | --- |
| `mobocom-VERSION.mbrelease` | **آپدیت سایت نصب‌شده از پنل وب**؛ مثلاً `mobocom-1.7.15.mbrelease` |
| `mobocom-setup-VERSION.run` | نصب اولیهٔ Ubuntu 22.04/24.04/26.04، Debian 12/13 یا AlmaLinux 9/10 و نصب ابزارهای مورد اعتماد میزبان؛ برای هر آپدیت معمول دوباره اجرا نمی‌شود |
| `mobocom-setup-VERSION.run.sha256` | بررسی سالم‌بودن فایل نصب؛ اصالت منبع دریافت هم باید بررسی شود |
| `release-public.pem` | کلید عمومی ناشر؛ کلید خصوصی نیست. کلید مورد اعتماد سرور را صرفاً از روی یک دانلود جدید عوض نکنید |
| `SHA256SUMS` | checksum فایل‌های همان انتشار؛ پیش از نصب با فایل‌های دریافت‌شده مقایسه کنید |
| `INSTALL-FA.md`، `UPGRADE-FA.md` و `RELEASES-FA.md` | راهنمای نصب، آپدیت/بازیابی و همین روند دریافت/انتشار |
| `Source code (zip)` یا `Source code (tar.gz)` | آرشیو خودکار سورس GitHub؛ **فایل قابل بارگذاری در آپدیتر نیست** |

نسخهٔ فعلی: **[MoboCom 1.7.15](https://github.com/WebNetData/MoboComCMS/releases/tag/v1.7.15)**. نسخهٔ بسته و پنل `1.7.15` است. شامل تأیید پیامکی اجباری موبایل از پنل، قالب یکپارچهٔ ایمیل‌ها، فروشگاه فایل، استایل فرم‌های ارسال مطلب، نام بخش‌ها از مدیریت، قیمت‌گذاری و رسانهٔ فروشگاه و Next.js 16.4.6 است. یک مهاجرت افزایشی برای افزایش قیمت ارزی گونه‌ها دارد. [یادداشت نسخه](releases/1.7.15.md) را بخوانید؛ نسخه‌های قبلی بازنویسی نمی‌شوند.

## فایل را چطور روی سایت نصب کنم؟

برای سایت نصب‌شده، `mbrelease` را روی کامپیوتر خود دانلود کنید؛ لازم نیست از قبل آن را با SFTP به پوشهٔ برنامه ببرید:

1. در سایت خود **پنل سرور ← به‌روزرسانی امن** (`/admin/updates`) را باز و با گذرواژهٔ مدیر، دسترسی پنل سرور را تأیید کنید.
2. فایل `mbrelease` را انتخاب و **بارگذاری و بررسی بسته** را بزنید. سقف بارگذاری ۵۱۲ مگابایت است. در این مرحله هنوز کد سایت عوض نمی‌شود.
3. نسخه و ناشر را بررسی و پشتیبان‌گیری اجباری را تأیید کنید؛ سپس نصب را شروع کنید. باید نسخهٔ بسته از نسخهٔ نصب‌شده بزرگ‌تر و کلید ناشر همان کلید مورد اعتماد سرور باشد.
4. صفحهٔ پیشرفت را باز نگه دارید. پس از راه‌اندازی مجدد، پنل را دوباره باز و وضعیت نهایی، ورود، رسانه و یک مسیر اصلی سایت را بررسی کنید.

سرور امضا را کنترل، کد را جداگانه آماده و از دیتابیس و فایل‌های تحت پوشش بکاپ می‌گیرد؛ بکاپ ناموفق مانع تعویض کد می‌شود. شکست ساخت سایت فعلی را نگه می‌دارد؛ شکست سلامت پس از تعویض، بازگشت کد قبلی را امتحان می‌کند. این سازوکار بدون‌قطعی نیست و دیتابیس را خودکار به گذشته برنمی‌گرداند. برای نگهداری بکاپ خارج از سرور، مسیرهای رسانهٔ قدیمی/بیرونی و محدودیت‌های بازیابی، [راهنمای آپدیت](UPGRADE-FA.md) را بخوانید.

### آیا این فایل، بیلد آمادهٔ Next.js است؟

`mbrelease` **بستهٔ انتشار امضاشدهٔ سورس** است؛ شامل `.next` یا `node_modules` کامپیوتر توسعه نیست. سرور وابستگی‌های قفل‌شده و بیلد سازگار با محیط Linux خودش را آماده می‌کند. شما فایل انتشار را بارگذاری می‌کنید و این کار را worker موجود انجام می‌دهد. بنابراین زمان و حافظهٔ کافی برای بیلد، دیسک برای نسخهٔ جدا و بکاپ و دسترسی به مخزن وابستگی‌ها لازم است؛ آپدیت کاملاً آفلاین یا بدون بیلد نیست.

کپی‌کردن `.next` یا جایگزین‌کردن کل پوشهٔ سایت با ZIP سورس، مسیر پشتیبانی‌شدهٔ ارتقا نیست. مسیر فعلی به GitHub روی سرور وابسته نیست؛ محل دریافت همین فایل‌ها می‌تواند هاست دانلود خودتان هم باشد و امضای ناشر همچنان بررسی می‌شود.

### اولین نصب یا نصب نیمه‌تمام

برای نصب تازه، فایل `run` همان نسخه را به سرور منتقل و اجرا کنید؛ دامنه، ایمیل، SSL، نام سایت و حساب مدیر در مرورگر وارد می‌شوند:

```bash
sudo bash mobocom-setup-1.7.15.run
```

برای نصب قدیمی نیمه‌تمام **پیش از ساخت اولین مدیر**:

```bash
sudo bash mobocom-setup-1.7.15.run --resume-uninstalled
```

ادامهٔ نصب با بررسی نبود مدیر/قفل پایان نصب، بکاپ اجباری و حفظ داده‌ها انجام می‌شود. برای سایت نصب‌شده از این گزینه استفاده نکنید. [راهنمای HTTPS اولیه، اثر انگشت گواهی و ادامهٔ نصب](INSTALL-FA.md).

## توسعه‌دهنده یا ایجنت: نسخهٔ بعدی را چطور منتشر کنم؟

این بخش روی کامپیوتر ناشر اجرا می‌شود، نه روی سرور سایت. ابزار بسته‌بندی موجود `scripts/build-release-package.cjs` است؛ سامانه یا workflow دیگری لازم نیست. Git محلی، Node22، Python3 و برای بارگذاری، [GitHub CLI](https://cli.github.com/manual/gh_release_create) لازم‌اند.

1. تغییرات کامل و تست‌شده را انتخاب کنید. برای نسخهٔ پایدار، PR به `main` مرج شود و همان commit نهایی دوباره بررسی شود؛ برای ارزیابی پیش از مرج، برچسب Pre-release اجباری است. مرج‌شدن PR به‌تنهایی فایل انتشار تولید نمی‌کند و نصب روی سرور را تغییر نمی‌دهد.
2. برای **هر انتشار دارای تغییر کد/رفتار** شمارهٔ نسخه را افزایش دهید؛ مثلاً `1.7.15` به `1.7.16`. نسخهٔ ریشه در `package.json` و `package-lock.json` باید یکسان باشد. مهاجرت‌ها را با manifest موجود تطبیق دهید؛ یک مهاجرت منتشرشده هرگز ویرایش نمی‌شود. سورس را commit کنید. بسته فقط از `HEAD` ثبت‌شده ساخته می‌شود؛ تغییرات ذخیره‌نشده وارد آن نمی‌شوند.
3. بررسی‌های مرتبط، بیلد و تست‌های محلی را روی همان سورس انجام دهید و نتیجهٔ واقعی، محدودیت‌ها و مسیر بازگشت را در handoff و یادداشت انتشار ثبت کنید. بدون اندازه‌گیری موفقیت اعلام نکنید؛ GitHub Actions برای ساخت/بارگذاری این بسته لازم نیست.
4. با **همان کلید خصوصی ناشر قبلی، خارج از مخزن** بسته بسازید. کلید جدید برای هر نسخه نسازید؛ سرور با کلید دیگری بسته را رد می‌کند. کلید خصوصی در GitHub، Release یا سرور سایت قرار نمی‌گیرد.

مثال Linux، با مسیرهای خودتان و پوشهٔ خروجی جدید/اختصاصی:

```bash
node scripts/build-release-package.cjs build /secure/distribution/1.7.16 /secure/offline/mobocom-keys/release-private.pem
```

مثال PowerShell:

```powershell
node scripts/build-release-package.cjs build "C:\MoboCom-Releases\1.7.16" "C:\Secure\mobocom-keys\release-private.pem"
```

کلید موجود ناشر را استفاده کنید؛ مسیر مثال جای نگهداری کلید واقعی شما را تعیین نمی‌کند. ابزار از نوشتن روی فایل خروجی موجود خودداری می‌کند. اگر `python3` یا `python` در PATH نیست، متغیر `PYTHON` را به executable معتبر بدهید.

5. امضا، نسخه و commit بسته، checksum نصب‌کننده، استخراج محدودشده و نبود داده/کلید خصوصی در خروجی را بررسی کنید. نسخهٔ آزمایشی را با همان مسیر آپدیت در محیط جدا تست کنید؛ اجرای صحیح ابزار بسته‌بندی به‌تنهایی تست عملکرد سایت نیست.
6. commit دقیق را روی GitHub push کنید. از صفحهٔ Releases → **Draft a new release** تگ نسخه و commit تأییدشده را انتخاب کنید؛ به پیش‌فرض `main` اعتماد نکنید. فایل‌های `mbrelease`، `run`، `run.sha256`، **کلید عمومی** و سه راهنما را در Assets قرار دهید. یادداشت نسخه باید commit، تغییرات، بررسی‌های اجراشده و نیازهای سرور/مهاجرت را مشخص کند.

برای انتشار از CLI، ابتدا `gh auth login` را روی کامپیوتر ناشر انجام دهید. نمونهٔ زیر برای نسخهٔ بعدی است؛ مقدار SHA را با commit واقعی **موجود در GitHub** عوض کنید و notes را در فایل بنویسید:

```bash
gh release create v1.7.16 /secure/distribution/1.7.16/mobocom-1.7.16.mbrelease /secure/distribution/1.7.16/mobocom-setup-1.7.16.run /secure/distribution/1.7.16/mobocom-setup-1.7.16.run.sha256 /secure/distribution/1.7.16/release-public.pem docs/INSTALL-FA.md docs/UPGRADE-FA.md docs/RELEASES-FA.md --repo WebNetData/MoboComCMS --target FULL_COMMIT_SHA --title "MoboCom 1.7.16" --notes-file /secure/distribution/1.7.16/notes.md --latest
```

برای انتشار پیش از مرج، به‌جای `--latest` از `--prerelease --latest=false` استفاده کنید. وضعیت پیش‌انتشار فقط نشان GitHub است؛ نسخهٔ داخل بسته همچنان عددی مثل `1.7.16` است. بستهٔ منتشرشده، فایل‌ها و تگ آن را عوض یا با `--clobber` بازنویسی نکنید. اصلاح بعدیِ کد نسخهٔ بالاتر می‌گیرد؛ آپدیتر نسخهٔ مساوی را نمی‌پذیرد. تبدیل همان پیش‌انتشار به پایدار فقط وقتی مجاز است که همان کد/commit بررسی‌شده در `main` حفظ شده باشد؛ در صورت تغییر، بستهٔ جدید با شمارهٔ بالاتر لازم است.

پس از انتشار، فایل‌ها را دوباره از GitHub دریافت و hash آن‌ها را با خروجی محلی مقایسه کنید. دانلود با حساب دارای دسترسی:

```bash
gh release download v1.7.16 --repo WebNetData/MoboComCMS --pattern '*.mbrelease' --pattern '*.run' --pattern '*.sha256' --pattern 'release-public.pem' --dir ./downloaded-1.7.16
```

ساخت بسته و بارگذاری Assets از GitHub Actions استفاده نمی‌کند. طبق تصمیم مالک، workflow بررسی PR و مرورگر دستی هستند؛ برای هر PR خودکار اجرا نمی‌شوند. طبق تصمیم مالک، تست مرورگر میزبانی‌شده خودکار تکرار نمی‌شود؛ کاهش مصرف Actions مجوز اعلام نتیجهٔ تست اجرا‌نشده نیست.

## اگر فایل آپدیت کار نکرد

| نشانه | بررسی |
| --- | --- |
| Assets یا نسخه را نمی‌بینم | وضعیت Draft/Pre-release و تگ دقیق نسخه را بررسی کنید |
| فایل رد می‌شود | فایل `mbrelease` را دانلود کنید، نه ZIP خودکار سورس؛ نسخه باید بزرگ‌تر و امضای ناشر معتبر باشد |
| نسخهٔ جدید در GitHub هست ولی سایت عوض نشده | انتشار مستقل از نصب است؛ فایل را از پنل سایت بارگذاری و عملیات نصب را اجرا کنید |
| فایل متعلق به commit قبلی است | توسعه‌دهنده باید از HEAD درست بسته بسازد و نسخهٔ بالاتر منتشر کند؛ اسم فایل یا manifest را دستی تغییر ندهید |
| بارگذاری ۴۱۳ یا قطع می‌شود | سقف Nginx/CDN/پراکسی را برای مسیر خصوصی آپدیت بررسی کنید؛ سقف خود برنامه ۵۱۲ مگابایت است |
| بیلد متوقف می‌شود | نتیجه و لاگ worker را در پنل بررسی کنید؛ RAM/دیسک/وابستگی‌ها را اصلاح کنید، داده و env را پاک نکنید |
| کلید ناشر فرق دارد | فایل ناشر درست را بگیرید؛ کلید مورد اعتماد سرور فقط با بررسی صریح اپراتور قابل تغییر است |

مسیرهای مرجع: [نصب](INSTALL-FA.md)، [آپدیت و بازیابی](UPGRADE-FA.md)، [پنل سرور](WEB_SETUP_AND_SERVER.md). مستندات رسمی ابزار انتشار: [ایجاد Release](https://cli.github.com/manual/gh_release_create)، [دریافت Assets](https://cli.github.com/manual/gh_release_download).
