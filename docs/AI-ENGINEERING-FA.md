# مهندسی و نگهداری هوشمند موبوکام

این بخش در «مدیریت ← پنل سرور ← مهندسی هوشمند» قرار دارد. مدیر می‌تواند
مشکل یا قابلیت دلخواه را توضیح دهد، مهارت مرتبط انتخاب کند و نتیجه، فایل‌های
تغییرکرده، بررسی‌ها و PR را ببیند. توسعه و ساخت PR خودکار است؛ مرج و سپس
تأیید انتشار همان نسخه با مالک است. این قابلیت به‌صورت پیش‌فرض خاموش است.

## مدل، دانش و هزینه

در تنظیمات هوش مصنوعی، کاربرد «مهندسی سایت» را تنظیم کنید. این کاربرد از
مسیر مدیر ارث می‌برد و می‌تواند اتصال اختصاصی داشته باشد. اتصال شخصی مدیر
فقط برای ابزارهای مدیریتی است؛ دسترسی کاربران سایت را گسترش نمی‌دهد.

بستهٔ دانش از معماری، نقشه، تصمیمات، راهنمای کیفیت و شش اسکیل محلی mobocom
ساخته می‌شود. هر درخواست نسخه و هش دانش و مهارت‌های انتخابی را نگه می‌دارد.
فقط قسمت مرتبط زیر سقف زمینه به مدل ارسال می‌شود. در همین صفحه می‌توانید
مهارت متنی اضافه، ویرایش، غیرفعال یا حذف کنید؛ مهارت مجوز اجرای فرمان نیست.
رمز، اطلاعات مشتری و کلید سرویس را داخل درخواست یا مهارت ننویسید.

سقف پیش‌فرض چهار فراخوانی مدل، ۲۴هزار نویسهٔ زمینه، شش‌هزار توکن خروجی در
هر فراخوانی و دوازده فایل است. هر تلاش پیش از ارسال رزرو می‌شود؛ پاسخ گم‌شده
خودکار دوباره خریداری نمی‌شود. دریافت وضعیت هزینهٔ مدل ندارد. «سقف خروجی
رزروشده» مصرف واقعی یا مبلغ صورتحساب ارائه‌دهنده نیست. حداکثر سه بیلد با
منبع متفاوت مجاز است؛ بیلد شکست‌خوردهٔ بدون تغییر تکرار نمی‌شود.

## جریان کار

1. «توسعه» یک شاخهٔ تمیز از main می‌سازد، فایل‌های مرتبط را می‌خواند و تغییر
   محدود پیشنهادشده توسط مدل را با هش قبلی اعمال می‌کند.
2. بررسی‌های ثابت، آزمون‌های مرتبط و یک بیلد در Docker غیرروت، بدون شبکه،
   با PostgreSQL خالی و جدا اجرا می‌شوند. دیتابیس، کلیدها و فایل‌های سایت
   اصلی در دسترس محیط بیلد نیستند.
3. پس از موفقیت، رسید بررسی و لینک تغییر به معماری/نقشه/دفتر قابلیت‌ها اضافه
   می‌شود، دانش همراه نسخه تازه می‌شود و PR به main ساخته می‌شود. متن خصوصی
   درخواست در عنوان PR یا رسید عمومی معماری کپی نمی‌شود. کد و diff پیش از
   انتشار همچنان باید از نظر اطلاعات خصوصی و رفتار بررسی شوند.
4. PR را بررسی و مرج کنید؛ تغییرات رابط را در مرورگر ببینید. سپس در پنل،
   انتشار همان هش کد و بسته را صریحاً تأیید کنید. سرور مرج دقیق، برابری درخت
   main، بایت‌های بسته، اختیار تازه، بکاپ و منابع را دوباره بررسی می‌کند.
5. نسخهٔ جدید در پوشهٔ جدا با همان کاربر سرویس و ابزارهای نصب‌شدهٔ میزبان
   بالا می‌آید. پس از آمادگی، Nginx به پورت جدید منتقل می‌شود؛ پاسخ عمومی
   باید شناسهٔ همان نسخه را داشته باشد. نسخهٔ قبلی برای بازگشت حفظ می‌شود.

«عیب‌یابی» فقط گزارش منابع و آمادگی می‌دهد. «پیشنهاد بازیابی» می‌تواند از
اقدام‌های ثابتِ بارگذاری مجدد Nginx، روشن‌کردن Nginx متوقف‌شده یا روشن‌کردن
نسخهٔ فعلی متوقف‌شده انتخاب کند. اجرای همان اقدام نیاز به تأیید جدا دارد؛
با تغییر وضعیت/نسخه، گزارش قدیمی معتبر نیست. این مسیر ترمینال عمومی نیست.

## نصب یک‌بارهٔ ابزار میزبان

رابط به‌تنهایی ابزار میزبان را نصب نمی‌کند. پروفایل فعلی مخصوص نصب متعارف
Ubuntu 24.04 به بعد، `/opt/mobocom/app`، کاربر `mobocom`، PostgreSQL، Nginx،
Docker و `/usr/bin/node` نسخهٔ ۲۲ است. سازگاری Node و glibc با تصویر وابستگی
ضروری است. نصب‌های دیگر به تطبیق و بررسی اپراتور نیاز دارند.

پس از نصب نسخهٔ حاوی این قابلیت، اجرای مهاجرت عادی انتشار و مرور اسکریپت:

```bash
bash /opt/mobocom/app/deploy/ubuntu/engineering-install.sh
```

اسکریپت از منبع commit‌شده وابستگی ثابت و worker مستقل می‌سازد، ابزار و
وابستگی‌های آن را root-owned کپی می‌کند و پیکربندی می‌نویسد. دیتابیس اصلی
را مهاجرت نمی‌دهد و ترافیک را جابه‌جا نمی‌کند. نصب موجود را بازنویسی نمی‌کند.
برای مخزن خصوصی، دسترسی clone/build اولیه را اپراتور باید فراهم کند.

فایل‌های تنظیمات:

| مسیر | کاربرد |
| --- | --- |
| `/etc/mobocom/engineering.json` | مخزن، هش وابستگی/تصویر، مسیرها و سقف منابع؛ root0600 |
| `/etc/mobocom/engineering-github.token` | توکن محدود به همین مخزن؛ root0600 |
| `/usr/local/lib/mobocom-engineering` | ابزار و worker و وابستگی ثابت، بدون دسترسی نوشتن برنامه |
| `/var/lib/mobocom-engineering` | شاخه‌ها، رسیدها و قفل‌های خصوصی؛ root0700 |
| `/opt/mobocom-engineering/releases` | کد نسخه‌های تأییدشده، فقط خواندنی برای سرویس |
| `/var/cache/mobocom-engineering` | کش قابل نوشتن هر نسخه |
| `/run/mobocom-engineering` | سوکت محلی و نشانگر نسخهٔ فعال |

توکن GitHub باید اجازهٔ خواندن/نوشتن محتوا و PR همان مخزن را داشته باشد؛
مجوز merge یا workflow لازم نیست. آن را در پنل، درخواست، CLI argument یا
مخزن قرار ندهید. ارتباط GitHub فقط در ابزار ثابت میزبان انجام می‌شود.

پروفایل پیش‌فرض برای سرور ۸ گیگابایتی، بیلد را به ۴GiB RAM و ۳GiB swap و
heap پنج‌گیگابایتی محدود می‌کند؛ PostgreSQL جدا ۳۸۴MiB و ذخیرهٔ میزبان
حداقل ۱GiB است. پیش‌بررسی حافظهٔ آزاد واقعی و swap مانع شروع نامناسب می‌شود.
اسکریپت swap نمی‌سازد. حفظ چند نسخه و فضای فایل‌ها به ظرفیت اضافه نیاز دارد؛
کمبود منابع باید با توقف بیلد حل شود، نه خاموش‌کردن سایت. سقف runtime هر
نسخه ۲GiB است. مقادیر را با مصرف واقعی سایت تطبیق دهید.

در `location /` فعلی Nginx، فقط `proxy_pass` را با این include جایگزین کنید؛
TLS، هدرها، timeout و locationهای اختصاصی را حفظ کنید:

```nginx
include /etc/nginx/mobocom-engineering-location.conf;
```

ابتدا `nginx -t` و سپس reload آرام انجام دهید. include اولیه به پورت ۳۰۰۰
اشاره می‌کند. پس از تنظیم توکن، پیکربندی و بکاپ موجود:

```bash
systemctl enable --now mobocom-ai-engineering-broker.service mobocom-ai-engineering-worker.service mobocom-ai-engineering-watchdog.timer
```

پورت‌های ۳۱۰۱/۳۱۰۲ باید فقط روی loopback و آزاد باشند. سرویس اولیهٔ
`mobocom` روی ۳۰۰۰ نگه داشته می‌شود؛ APIهای کنترل سرور به آن هدایت می‌شوند
تا اختیار فایل‌ها و ابزارهای همان میزبان باقی بماند. ورود مجدد، محدودیت IP،
دو مرحله‌ای، Origin و مجوزهای `server.manage` و `settings.manage` برقرارند.
worker مستقل از HTTP سایت از همان صف BackgroundJob استفاده می‌کند؛ در قطع
پیش‌نمایش ادامه می‌دهد. قطع دیتابیس/میزبان همچنان مداخلهٔ اپراتور می‌خواهد.

## بازگشت، محدودیت‌ها و ارتقای ابزار

بازگشت فقط کد و مسیر Nginx را عوض می‌کند؛ بکاپ قدیمی روی دادهٔ جدید مشتری
بازنویسی نمی‌شود. پایش مستقل، در بازهٔ پیش‌فرض ۳۰ دقیقه پس از انتشار، فقط به
نسخهٔ قبلیِ سالم برمی‌گردد. این ضمانت رفع همهٔ خرابی‌ها یا قطعی صفر نیست.
سرویس‌های نسخه با unit ماندگار systemd از reboot عبور می‌کنند. فقط runtime
فعال مالک زمان‌بندی‌های پس‌زمینه است؛ نسخه‌های قبلی داده را پاک نمی‌کنند.

تغییر schema، مهاجرت، وابستگی، ابزار امنیت/هویت/AI، تنظیم میزبان یا workflow
در محدودهٔ توسعهٔ خودکار نیست. این کارها از انتشار عادی بررسی‌شده می‌گذرند.
تا وقتی نسخهٔ مدیریت‌شده فعال است، Updater درجا مسدود می‌شود تا درخت زنده و
دیتابیس جداگانه تغییر نکنند. برای انتشار عادی، ابتدا با اختیار مالک به native
سالم و سازگار برگردید، سپس راهنمای انتشار عادی را دنبال کنید. downgrade
ناسازگار با schema مجاز نیست. داده و تاریخچهٔ workflow را نگه دارید.

برای ارتقای ابزار root، کارهای فعال را تمام/لغو و قابلیت را خاموش کنید؛ از
پیکربندی و رسیدها پشتیبان بگیرید، نسخهٔ جدید ابزار، bundle worker و تصویر
وابستگی را از commit مرورشده در مسیر موقت بسازید، سازگاری/`--check` را بررسی
و با نگه‌داشتن نسخهٔ قبلی به‌صورت کنترل‌شده جایگزین کنید. هش lock جدید باید
با main یکی باشد. ابزار root از داخل درخواست یا مهارت خود را ارتقا نمی‌دهد.
پوشه‌های انتشار/volume قدیمی را خودکار پاک نمی‌کنیم؛ پاکسازی فقط پس از
بررسی نسخهٔ فعال، نسخهٔ بازگشت و رسیدها توسط اپراتور انجام شود.
