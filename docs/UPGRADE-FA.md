# آپدیت بدون از دست رفتن اطلاعات

این راهنما برای سایتی است که با [راهنمای نصب](INSTALL-FA.md) روی اوبونتو نصب شده. راهنمای Coolify و هاست در انتهای همین صفحه است.

## چرا اطلاعات از بین نمی‌رود

آپدیت فقط کد برنامه را عوض می‌کند. اطلاعات شما جای دیگری است:

| چه چیزی | کجاست | در آپدیت |
| --- | --- | --- |
| کد برنامه | `/opt/mobocom/app` | عوض می‌شود |
| کاربران، سفارش‌ها، مطالب، تنظیمات | دیتابیس PostgreSQL | می‌ماند و فقط طرح آن با مهاجرت‌ها کامل می‌شود |
| فایل‌های آپلودشده | `/opt/mobocom/app/storage` | دست نمی‌خورد |
| کلیدها و تنظیمات سرور | `/etc/mobocom/mobocom.env` | دست نمی‌خورد |

## آپدیت در یک دستور

اول وضعیت را ببینید:

```bash
sudo mobocom status
```

بعد آپدیت کنید:

```bash
sudo mobocom update
```

تا پایان کار، سایت چند دقیقه کند یا ناپایدار است؛ پس زمان خلوت را انتخاب کنید. پایان موفق با این خط مشخص می‌شود:

```text
[update] healthy
```

### دستور آپدیت به این ترتیب کار می‌کند

1. **بررسی:** فضای دیسک، اجازهٔ راه‌اندازی مجدد و نبودن تغییر محلی در کد را بررسی می‌کند. اگر مشکلی باشد، پیش از هر تغییری متوقف می‌شود.
2. **پشتیبان:** از دیتابیس و فایل‌ها پشتیبان می‌گیرد و سلامت آن را می‌سنجد. اگر پشتیبان خراب باشد، آپدیت ادامه پیدا نمی‌کند.
3. **کد تازه:** کد جدید را می‌گیرد، وابستگی‌ها را نصب و برنامه را می‌سازد.
4. **راه‌اندازی:** سرویس را دوباره بالا می‌آورد و مهاجرت‌های دیتابیس همان موقع اجرا می‌شوند.
5. **بررسی سلامت:** ۱۲۰ تلاش با فاصلهٔ سه ثانیه و مهلت پنج ثانیه برای هر درخواست؛ در کندترین حالت ممکن است بیشتر از شش دقیقه طول بکشد.
6. **برگشت خودکار:** اگر ساخت یا راه‌اندازی شکست بخورد و تغییر محلی تازه‌ای ایجاد نشده باشد، کد قبلی را برمی‌گرداند و دوباره می‌سازد. کار محلی تازه حفظ می‌شود و بازیابی کد به بررسی اپراتور نیاز دارد.

برگشت خودکار فقط کد را برمی‌گرداند و مهاجرت‌های دیتابیس را برنمی‌گرداند. سازگاری نسخهٔ قبلی با مهاجرت جدید باید در همان انتشار تأیید شده باشد. ساخت روی همین پوشه انجام می‌شود؛ این روش تضمین بدون‌قطعی نیست و به فضای دیسک، حافظه و بررسی سلامت نیاز دارد.

## اگر بعد از آپدیت مشکلی دیدید

از راه اول شروع کنید و فقط اگر لازم بود سراغ راه بعدی بروید.

### راه اول: برگشت به نسخهٔ قبلی

سایت بالا آمده ولی نسخهٔ جدید مشکلی دارد:

```bash
sudo mobocom rollback
```

این دستور فقط کد را برمی‌گرداند. **هیچ اطلاعاتی از دست نمی‌رود** و هر چیزی که بعد از آپدیت ثبت شده می‌ماند. دفعهٔ بعد `sudo mobocom update` دوباره سایت را به آخرین نسخه می‌برد.

### راه دوم: بازگردانی پشتیبان

فقط وقتی اطلاعات واقعاً خراب شده‌اند، مثلاً یک مهاجرت نیمه‌کاره سایت را از کار انداخته. فهرست پشتیبان‌ها را ببینید و یکی را برگردانید:

```bash
sudo mobocom backups
sudo mobocom restore 20261031-033000
```

به‌جای نام می‌توانید `latest` بنویسید. دستور از شما می‌خواهد `RESTORE` را تایپ کنید.

> **هشدار:** هر چیزی که بعد از آن پشتیبان ثبت شده، مثل سفارش‌ها و ثبت‌نام‌های تازه، از دیتابیس برمی‌گردد. برای همین این راه آخرین راه است.

دستور ابتدا کپی خصوصی پشتیبان را با کاربر سرویس بررسی و آماده می‌کند، سپس سایت را متوقف می‌کند و از وضعیت فعلی پشتیبان می‌گیرد. اگر پشتیبان فعلی شکست بخورد، جایگزینی انجام نمی‌شود و سایت دوباره راه می‌افتد. فایل‌ها جابه‌جا می‌شوند و دیتابیس با یک تراکنش بازیابی می‌شود؛ شکست تراکنش، فایل‌های قبلی را هم برمی‌گرداند. فایل‌های پیشین در مسیر خصوصی `.restore.*` کنار برنامه نگه داشته می‌شوند.

تنظیمات فعلی `storage/config`، تاریخچه و قفل آپدیت و پشتیبان‌های داخلی حفظ می‌شوند. برای انتقال کامل به سرور جدید، تنظیمات و کلیدهای سازگار را جداگانه بازیابی کنید. فقط پشتیبان مورد اعتماد خودتان را استفاده کنید: آرشیو دیتابیس می‌تواند SQL اجرا کند. [مستندات PostgreSQL](https://www.postgresql.org/docs/current/app-pgrestore.html) تضمین تراکنش را برای دیتابیس توضیح می‌دهد؛ تراکنش واحدی میان دیتابیس و فایل‌سیستم وجود ندارد.

قطع برق، `kill -9` یا خرابی دیسک هنگام جابه‌جایی ممکن است به بازیابی دستی نیاز داشته باشد. قفل را صرفاً به‌خاطر قدیمی‌بودن حذف نکنید. اگر جبران فایل‌ها شکست خورد، سرویس خاموش می‌ماند؛ مسیر خصوصی و پشتیبان ایمنی را نگه دارید. اگر دیتابیس بازیابی شد ولی بررسی سلامت شکست خورد، دادهٔ بازیابی‌شده حفظ می‌شود؛ نسخهٔ برنامه و مهاجرت‌ها را بررسی کنید. کارهای زمان‌بندی‌شدهٔ بیرونی و هر سرویس دیگری که در دیتابیس می‌نویسد را قبل از بازیابی متوقف کنید.

پشتیبان نسخهٔ قدیمی را ابتدا در محیط جدا آزمایش کنید؛ بازیابی آرشیو، جدول‌های اضافه‌شده در نسخه‌های جدیدتر را خودکار حذف نمی‌کند و اجرای دوبارهٔ مهاجرت‌ها ممکن است با آن‌ها برخورد کند. تست این بسته بازیابی schema فعلی را تأیید کرده است، نه همهٔ ترکیب‌های تاریخی نسخه‌ها.

## پشتیبان‌گیری

پشتیبان خودکار هر شب حدود ساعت ۳:۳۰ گرفته می‌شود و ۱۴ روز در `/var/backups/mobocom` می‌ماند.

```bash
sudo mobocom backup     # همین الان یک پشتیبان بگیر
sudo mobocom backups    # فهرست پشتیبان‌ها
```

> پشتیبانی که فقط روی همان سرور باشد، با خرابی سرور از بین می‌رود.

دست‌کم هفته‌ای یک بار از کامپیوتر خودتان یک نسخه بگیرید:

```bash
rsync -az root@IP_SERVER:/var/backups/mobocom/ ./mobocom-backups/
```

فایل `/etc/mobocom/mobocom.env` جزو پشتیبان نیست. نسخهٔ بیرون از سرور آن را طبق [راهنمای نصب](INSTALL-FA.md#یک-کار-مهم-بعد-از-نصب) نگه دارید. فایل‌های میزبان رمزگذاری نشده‌اند و ممکن است تنظیمات خصوصی `storage/config` را هم داشته باشند؛ فقط مالک دسترسی دارد. انتقال و نگهداری خارج از سرور را امن انجام دهید. این‌ها با بکاپ رمزگذاری‌شدهٔ داخل پنل متفاوت‌اند.

## کارهایی که نباید انجام دهید

| کار | چرا |
| --- | --- |
| `prisma db push` روی سایت واقعی | می‌تواند ستون‌ها و داده‌ها را حذف کند. |
| اجرای دوبارهٔ `deploy:seed` روی سایت واقعی | فقط برای نصب اول است. |
| تغییر `PANEL_CREDENTIAL_KEY` | اطلاعات رمزشده دیگر خوانده نمی‌شوند. |
| حذف یا ویرایش پوشه‌های `prisma/migrations` | تاریخچهٔ دیتابیس به هم می‌ریزد. |
| ویرایش مستقیم فایل‌های کد روی سرور | آپدیت را متوقف می‌کند. |
| `docker compose down -v` | پوشه‌های دائمی دیتابیس را پاک می‌کند. |

## پیام‌های رایج آپدیت

| پیام | معنی | راه‌حل |
| --- | --- | --- |
| `MB free; at least ... MB is needed` | دیسک برای ساخت کم است. چیزی تغییر نکرده. | فضا آزاد کنید و دوباره اجرا کنید. |
| `this user may not restart the service` | اجازهٔ راه‌اندازی مجدد تنظیم نشده. | `sudo bash /opt/mobocom/app/deploy/ubuntu/updater-install.sh` |
| `local changes must be resolved` | فایل‌های کد یا فایل جدید ثبت‌نشده وجود دارند. | تغییرها را حفظ و بررسی کنید: `sudo -u mobocom git -C /opt/mobocom/app status`؛ از `reset --hard` برای پاک‌کردن آن‌ها استفاده نکنید. |
| `local commit history diverges` | کد سرور کامیتی دارد که در مخزن نیست. | پیش از آپدیت آن را تعیین تکلیف کنید. |
| `another update is running` | آپدیت یا بازیابی دیگری قفل را گرفته است. | صبر کنید؛ اپراتور باید نبود پردازش فعال و وضعیت سرویس را پیش از برداشتن قفل تأیید کند. |
| `application rolled back` | نسخهٔ جدید بالا نیامد و نسخهٔ قبلی برگشت. | `sudo journalctl -u mobocom -n 80 --no-pager` را بررسی کنید. |

## اگر سایت را پیش از این ابزار نصب کرده‌اید

اگر دستور `mobocom` روی سرور نیست، این کار را فقط یک بار انجام دهید:

```bash
cd /opt/mobocom/app
sudo mkdir -p /var/backups/mobocom && sudo chown mobocom:mobocom /var/backups/mobocom
sudo -u mobocom bash deploy/ubuntu/backup.sh
sudo -u mobocom git pull --ff-only origin main
sudo bash deploy/ubuntu/updater-install.sh
sudo install -m 755 deploy/ubuntu/mobocom /usr/local/bin/mobocom
sudo mobocom update
```

## آپدیت از پنل مدیریت

صفحهٔ **سرور ← به‌روزرسانی امن** همان مسیر امن را با یک کلیک اجرا می‌کند، با این شرط‌ها:

- ابزار پنل یک بار با `sudo bash deploy/ubuntu/updater-install.sh` نصب شده باشد.
- فایل‌های نصب ابزار دارای دسترسی ریشه را ابتدا از مخزن مورد اعتماد بررسی کنید. نصب‌کننده فقط محدودیت `NoNewPrivileges` را برای مجوز محدود sudo کنار می‌گذارد؛ سایر محدودیت‌های سرویس حفظ می‌شوند. سرویس باید بعد از نصب ابزار دوباره راه‌اندازی شود. مجوز عمومی sudo داده نمی‌شود.
- برای نسخهٔ جدید یک **GitHub Release** با tag منتشر شده باشد. پنل فقط نسخه‌های منتشرشده را نشان می‌دهد.
- برای مخزن خصوصی، سرور بتواند فهرست نسخه‌ها را بخواند.

تا وقتی Release منتشر نشده، از `sudo mobocom update` استفاده کنید که آخرین کد شاخهٔ `main` را نصب می‌کند.

## Coolify یا Docker

1. پشتیبان PostgreSQL و فضای `/app/storage` را بررسی کنید.
2. در Coolify روی **Redeploy** بزنید یا کد جدید را push کنید.
3. ایمیج جدید ساخته می‌شود و مهاجرت‌ها موقع راه‌اندازی اجرا می‌شوند.
4. `/api/health/ready` را بررسی کنید.

اطلاعات در volumeهای دائمی می‌ماند. برگشت: در Coolify نسخهٔ قبلی را دوباره deploy کنید. جزئیات: [Coolify](DEPLOY-COOLIFY.md).

## هاست cPanel یا DirectAdmin

پوشهٔ `storage` در بستهٔ آپلود نیست و دست نمی‌خورد. پیش از شروع، با ابزار Backup هاست از دیتابیس و `storage` پشتیبان بگیرید و سپس [قدم‌های آپدیت هاست](DEPLOY-VPS-HOST-FA.md#قدم-۸--به‌روزرسانی-روی-هاست) را انجام دهید.
