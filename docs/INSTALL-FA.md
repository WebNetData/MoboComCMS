# نصب موبوکام

دو راه دارد: **یک دستور** که کد را از GitHub می‌گیرد و ساده‌ترین راه است، و **فایل نصب امضاشده** (`.run`) برای سروری که نباید به GitHub وصل شود.

## نصب با یک دستور

**سیستم‌عامل‌ها:** Ubuntu 22.04، 24.04 و 26.04 LTS؛ Debian 12 و 13؛ AlmaLinux 9 و 10. سرور تازه با دسترسی root یا sudo، حداقل ۴ گیگ رم (۸ گیگ پیشنهاد می‌شود) و ۴۰ گیگ دیسک.

روی سرور فقط همین را اجرا کنید:

    curl -fsSL https://raw.githubusercontent.com/WebNetData/MoboComCMS/main/install.sh | sudo bash

اگر شبکهٔ سرور `raw.githubusercontent.com` را باز نمی‌کند ولی `github.com` باز است (مثل بسیاری از سرورهای داخل ایران)، همان نصب از این راه:

    cd /tmp && git clone --depth 1 https://github.com/WebNetData/MoboComCMS.git mobocom-src && sudo bash mobocom-src/install.sh

اگر `git` روی سرور نیست، اول `sudo apt-get install -y git` (در AlmaLinux: `sudo dnf install -y git`) را اجرا کنید.

#### سرور با اینترنت محدود

نصب‌کننده خودش تشخیص می‌دهد کدام سرویس‌ها از سرور در دسترس نیستند و فقط برای همان‌ها از مسیر جایگزین استفاده می‌کند. تنظیمی لازم نیست:

| اگر این بسته باشد | از کجا گرفته می‌شود | بررسی امنیتی |
| --- | --- | --- |
| `apt.postgresql.org` یا `download.postgresql.org` | همان بسته‌های رسمی PostgreSQL از میرور `mirrors.aliyun.com` | کلید امضای PostgreSQL فقط با اثر انگشت رسمی پذیرفته می‌شود و هر بسته با آن امضا بررسی می‌شود |
| `registry.npmjs.org` | اولین میرور در دسترس از این فهرست: Runflare، Liara و Huawei Cloud. در هر آپدیت دوباره بررسی می‌شود و اگر میرور قبلی از کار افتاده باشد، میرور بعدی انتخاب می‌شود | هر بسته با hash ثبت‌شده در `package-lock.json` بررسی می‌شود |
| `binaries.prisma.sh` | موتورهای رسمی Prisma از شاخهٔ `prisma-engines` همین مخزن در GitHub | فایل‌ها با SHA-256 منتشرشدهٔ Prisma که در کد ثبت شده مقایسه می‌شوند؛ فایل نامطابق نصب نمی‌شود |

برای استفادهٔ همیشگی از این مسیرها `--mirrors` و برای استفاده‌نکردن از آن‌ها `--no-mirrors` را به انتهای دستور نصب اضافه کنید.

**گواهی SSL:** اگر `acme-v02.api.letsencrypt.org` از سرور باز نشود، گواهی رایگان Let's Encrypt (هم روش HTTP و هم DNS کلادفلر) روی همین سرور صادر نمی‌شود. نصب‌کننده در پایان این را اعلام می‌کند. در ویزارد گزینهٔ **گواهی آماده (PEM)** را انتخاب کنید، مثلاً یک Cloudflare Origin Certificate (وقتی دامنه پشت کلادفلر است) یا گواهی خریداری‌شده.

این دستور سیستم را می‌شناسد و این کارها را انجام می‌دهد. سؤالی نمی‌پرسد و حدود ۱۰ تا ۲۰ دقیقه طول می‌کشد:

- نصب Node.js 22، PostgreSQL 17، Redis (در AlmaLinux 10 و Debian 13 در صورت نبود آن، Valkey که همان پروتکل را دارد)، Nginx و Certbot؛
- ساخت کاربر محدود `mobocom`، پایگاه داده با رمز تصادفی و فایل تنظیمات خصوصی؛
- گرفتن کد، ساخت سایت و راه‌اندازی سرویس؛
- فعال‌کردن بکاپ روزانه و دستور `mobocom`؛
- باز کردن پورت‌های SSH، 80، 443 و پورت موقت 8443 در فایروال: ufw در Ubuntu و Debian، firewalld در AlmaLinux. برای دست‌نخوردن فایروال، `-s -- --no-firewall` را به انتهای `sudo bash` اضافه کنید.

در AlmaLinux، SELinux روشن می‌ماند و فقط اجازهٔ اتصال Nginx به برنامه داده می‌شود (`httpd_can_network_connect`). مخازن EPEL و CRB هم برای Certbot فعال می‌شوند.

صبر کنید پیام `Installed` بیاید. سپس نشانی موقت `https://SERVER_IP:8443/install`، اثر انگشت گواهی و کد نصب نمایش داده می‌شود؛ ادامه دقیقاً مانند بخش [ادامه در مرورگر](#ادامه-در-مرورگر) است. فایروال ارائه‌دهندهٔ سرور (پنل ابری) را جداگانه برای این پورت‌ها باز کنید.

اجرای دوبارهٔ همین دستور روی سرور نصب‌شده بی‌خطر است: تنظیمات، دیتابیس، فایل‌ها و کد موجود را جایگزین نمی‌کند و فقط مرحله‌های ناتمام را کامل می‌کند.

### آپدیت و برگشت به نسخهٔ قبلی

پس از نصب، همه‌چیز با یک دستور کوتاه است:

    sudo mobocom update              # آخرین نسخه
    sudo mobocom versions            # نسخه‌های منتشرشده و نسخهٔ نصب‌شده
    sudo mobocom update 1.7.4        # رفتن به یک نسخهٔ مشخص جدیدتر
    sudo mobocom downgrade 1.6.1     # برگشت به یک نسخهٔ قدیمی‌تر
    sudo mobocom rollback            # برگشت به نسخهٔ پیش از آخرین آپدیت
    sudo mobocom status              # سلامت سایت، نسخه و آخرین بکاپ
    sudo mobocom panel on            # روشن کردن پنل سرور؛ با --ip YOUR.IP.ADDRESS فقط برای IP شما

در هر آپدیت یا برگشت، اول از دیتابیس و فایل‌ها بکاپ گرفته می‌شود، سپس کد عوض و سایت ساخته می‌شود و سلامت آن بررسی می‌شود. اگر سایت بالا نیاید، نسخهٔ قبلی خودبه‌خود برمی‌گردد. `downgrade` قبل از شروع توضیح می‌دهد چه می‌شود و تأیید `DOWNGRADE` می‌خواهد.

برگشت نسخه فقط کد را عوض می‌کند. سفارش‌ها، کاربران، نوشته‌ها و فایل‌ها می‌مانند و دیتابیس عقب برده نمی‌شود. اگر داده را هم باید به روز قبل برگردانید، پس از آن یکی از بکاپ‌ها را بازیابی کنید (`sudo mobocom backups` و `sudo mobocom restore NAME`؛ [توضیح کامل](UPGRADE-FA.md#پشتیبان-و-بازیابی-داده)).

نسخه‌ها همان tagهای `vX.Y.Z` مخزن‌اند و هر نسخهٔ جدید با انتشار ناشر در این فهرست می‌آید ([روند انتشار](RELEASES-FA.md)). روی سرورهای قدیمی‌تر که دستور `mobocom` آن‌ها هنوز `versions` و `downgrade` را ندارد، همان دستور یک‌خطی با یک کلمه در انتها این کارها را انجام می‌دهد و دستور `mobocom` را هم تازه می‌کند:

    curl -fsSL https://raw.githubusercontent.com/WebNetData/MoboComCMS/main/install.sh | sudo bash -s -- update
    curl -fsSL https://raw.githubusercontent.com/WebNetData/MoboComCMS/main/install.sh | sudo bash -s -- downgrade 1.6.1

نصبی که با فایل `.run` انجام شده، با بسته‌های امضاشده از **پنل سرور ← به‌روزرسانی امن** آپدیت می‌شود و این دستورها او را به همان‌جا راهنمایی می‌کنند.

## نصب با فایل امضاشده، بدون GitHub

نصب بسته‌ای به Git، حساب GitHub، Deploy Key یا توکن مخزن نیاز ندارد. یک فایل نصب روی سرور اجرا می‌کنید و ساخت مدیر و تنظیمات سایت را در مرورگر تمام می‌کنید. دسترسی به مخازن Ubuntu، Node.js، PostgreSQL و npm برای پیش‌نیازها لازم است؛ نصب کاملاً آفلاین نیست.

**فایل نصب:** از Assets نسخهٔ موردنظر در [GitHub Releases](https://github.com/WebNetData/MoboComCMS/releases)، فایل `mobocom-setup-VERSION.run` و checksum همراهش را بگیرید. فایل را روی کامپیوتر خود دانلود کنید و سپس به سرور منتقل کنید. ZIP خودکار سورس فایل نصب نیست. [دریافت فایل‌ها و روند نسخه‌های بعدی](RELEASES-FA.md).

## پیش‌نیاز

- Ubuntu 22.04، 24.04 یا 26.04 LTS، Debian 12 یا 13، یا AlmaLinux 9 یا 10؛ دسترسی SSH و sudo، حداقل ۴ گیگ رم و ۴۰ گیگ دیسک؛ ۸ گیگ رم پیشنهاد می‌شود.
- رکورد A دامنه به IP سرور و در صورت استفاده، رکورد صحیح AAAA و www؛ ورود به ویزارد اولیه با IP هم ممکن است.
- فایل مورد اعتماد mobocom-setup-VERSION.run از ناشر یا هاست دانلود خودتان. آن را با SCP/SFTP روی سرور بگذارید. پروژه به‌تنهایی نشانی عمومی دانلود ایجاد نمی‌کند.

## یک دستور روی سرور

برای بستهٔ 1.7.4 فقط همین دستور را اجرا کنید؛ دامنه و ایمیل را در مرورگر وارد می‌کنید:

    sudo bash mobocom-setup-1.7.4.run

پیش از اجرا، فایل و SHA-256 آن را از منبع مورد اعتماد بررسی کنید؛ نصب با sudo پیش‌نیازهای سیستم را آماده می‌کند. نصب‌کننده Node22، PostgreSQL17، Redis، Nginx و ابزار SSL را نصب، امضای بسته را بررسی و برنامه را می‌سازد. دریافت کد از داخل همان فایل است؛ اتصال به GitHub لازم نیست. برنامه با کاربر محدود mobocom اجرا می‌شود و ابزارهای دارای اختیار ریشه از نسخهٔ مورد اعتماد بسته نصب می‌شوند.

صبر کنید پیام نهایی `Installed` نمایش داده شود. `Compiled successfully` هنوز پایان بررسی TypeScript و ساخت نیست. پس از آن نشانی موقت شبیه `https://SERVER_IP:8443/install`، اثر انگشت SHA256 گواهی و کد خصوصی نصب در ترمینال نمایش داده می‌شود. اگر سرور پشت NAT است، IP عمومی خود را در همان نشانی استفاده کنید. در فایروال ارائه‌دهنده نیز پورت TCP8443 را برای IP خود باز کنید؛ UFW محلی در حالت عادی آن را باز می‌کند.

## ادامه در مرورگر

1. نشانی موقت HTTPS را باز کنید. گواهی اولیه خودامضاست؛ اثر انگشت نمایش‌داده‌شده در مرورگر را با ترمینال SSH مورد اعتماد مقایسه و سپس آن را برای همین نصب بپذیرید. قبل از تأیید گواهی، کد و رمزها را وارد نکنید. این گواهی موقت جای گواهی دامنه را نمی‌گیرد.
2. کد خصوصی نصب را وارد کنید؛ کد در URL قرار نمی‌گیرد.
3. در **دامنه و SSL** نام دامنه، گزینهٔ www و یکی از روش‌های زیر را انتخاب کنید. برای صدور خودکار، ایمیل دریافت گواهی و تأیید شرایط Let’s Encrypt هم در همین صفحه است. ایمیل حساب مدیر جداگانه در مرحلهٔ مدیر وارد می‌شود.
4. پس از آماده‌شدن HTTPS، نام سایت، مشخصات مدیر، گذرواژه و بخش‌های فعال را وارد کنید. در زمان راه‌اندازی مجدد سرویس صفحه را باز نگه دارید؛ تازه‌کردن صفحه هم تنظیمات ذخیره‌شده را نگه می‌دارد.
5. پس از ساخت اولین مدیر، ویزارد و درگاه موقت8443 بسته می‌شوند؛ از لینک ورود روی دامنهٔ نهایی استفاده کنید. احراز هویت دومرحله‌ای مدیر را هم فعال کنید. در صورت شکست بستن درگاه، هشدار را پیگیری کنید؛ API همچنان به‌دلیل وجود مدیر بسته است. پورت8443 را در فایروال ارائه‌دهنده نیز ببندید.

| روش SSL در ویزارد | آنچه لازم است |
| --- | --- |
| گواهی رایگان خودکار | رکورد A و در صورت وجود AAAA درست، پورت عمومی80 برای HTTP challenge؛ ایمیل و موافقت صدور. www فقط با رکورد خودش انتخاب شود. |
| اعتبارسنجی DNS کلادفلر | توکن محدود Zone:DNS:Edit برای دامنهٔ خودتان و ایمیل؛ افزونهٔ Certbot توسط bootstrap نصب می‌شود. توکن در تنظیمات رمزگذاری و نسخهٔ مخصوص تمدید در مسیر خصوصی root ذخیره می‌شود. |
| گواهی آماده | فایل PEM گواهی/زنجیره و کلید خصوصی بدون رمز فایل؛ تطابق کلید، SAN دامنه و اعتبار زمانی بررسی می‌شوند. تمدید این گواهی با بارگذاری نسخهٔ جدید است. |

برای ورود اولیه به ویزارد به DNS دامنه احتیاجی نیست؛ برای بازشدن سایت روی دامنهٔ نهایی باید DNS را تنظیم کنید. صدور گواهی نیازمند دسترسی به مرجع گواهی است؛ آپلود PEM این مرحله را ندارد. در حالت خودکار سرویس Nginx برای اعتبارسنجی متوقف نمی‌شود. SSL و دامنه بعداً از پنل سرور قابل مدیریت‌اند؛ Docker/Coolify همچنان پراکسی و SSL میزبان خودشان را دارند و ابزار root اوبونتو خودکار داخل آن‌ها نصب نمی‌شود.

مسیر استاندارد /opt/mobocom/app است. اجرای هم‌زمان نصب دوم رد می‌شود. اجرای عادی مجدد، داده و کد موجود را جایگزین نمی‌کند. دستور قدیمی با گزینه‌های صریح `--domain example.com --email owner@example.com` برای سازگاری حفظ شده است؛ دستور بدون آرگومان مسیر پیشنهادی وب است.

### ادامهٔ نصب نیمه‌تمام قدیمی

اگر نسخهٔ قدیمی مثل1.6.0 پیش از ساخت مدیر متوقف شده، فایل جدید و معتبر را به سرور منتقل و اجرا کنید:

    sudo bash mobocom-setup-1.7.4.run --resume-uninstalled

این گزینه اجازهٔ صریح جایگزینی کد نیمه‌تمام با بستهٔ امضاشدهٔ جدید است. ابتدا نبود مدیر/قفل پایان نصب و دسترسی به دیتابیس بررسی می‌شود؛ ساخت جداگانه و بکاپ موفق پیش از تعویض کد اجباری است. دیتابیس، env، کد خصوصی نصب و فایل‌های کاربران حفظ می‌شوند. وجود مدیر، غیرفعال‌بودن نصب یا خطای خواندن دیتابیس باعث توقف امن است؛ برای سایت نصب‌شده از آپدیت عادی پنل استفاده کنید. فایل قدیمی نصب خودش به نسخهٔ جدید تبدیل نمی‌شود. قبل از ادامه مطمئن شوید بیلد یا نصب دیگری فعال نیست. داده یا installed.lock را برای دورزدن این بررسی حذف نکنید.

از این پس در **پنل سرور ← به‌روزرسانی امن** فایل mbrelease نسخهٔ جدید را بارگذاری و نصب کنید. بازکردن مجدد پنل رمز مدیر می‌خواهد؛ مدیرِ فقط مجله این دسترسی را ندارد.

## پنل سرور با یک دستور

پنل سرور (فایل‌ها، پایگاه داده، دامنه و SSL، به‌روزرسانی، پروکسی و…) برای امنیت به‌طور پیش‌فرض خاموش است. روشن کردن آن یک دستور روی سرور است:

    sudo mobocom panel on --ip YOUR.IP.ADDRESS

- **نتیجه:** پنل روشن می‌شود و فقط از IP شما باز می‌شود. سایت دوباره راه‌اندازی و سلامت آن بررسی می‌شود و نشانی پنل (`/admin/server`) نمایش داده می‌شود.
- **چند IP یا یک بازه:** با کاما جدا کنید، مثل `--ip 1.2.3.4,5.6.7.0/24`.
- **بدون `--ip`:** پنل از هر IP باز می‌شود. دستور، IP اتصال SSH فعلی شما را برای محدود کردن پیشنهاد می‌دهد.
- **دستورهای دیگر:** `sudo mobocom panel status` وضعیت، `sudo mobocom panel off` خاموش کردن و `sudo mobocom panel on --any-ip` برداشتن محدودیت IP.

پس از روشن شدن، با حساب مدیر وارد `/admin/server` شوید و برای باز کردن قفل پنل، گذرواژه (و کد دومرحله‌ای، اگر فعال است) را دوباره وارد کنید. اگر دستور `mobocom` روی سرور قدیمی است و `panel` را نمی‌شناسد، همان دستور نصب یک‌خطی با کلمهٔ `panel on` در انتها کار را انجام می‌دهد و دستور را هم تازه می‌کند.

## پروکسی شبکه‌های اجتماعی (Xray)

اگر سرور به تلگرام و اینستاگرام دسترسی ندارد (مثل بسیاری از سرورهای داخل ایران)، ربات و مینی‌اپ تلگرام، ارسال خودکار به کانال تلگرام و انتشار در اینستاگرام از یک پروکسی Xray روی همین سرور استفاده می‌کنند:

1. نصب‌کننده هستهٔ Xray-core را خودش نصب می‌کند. روی سروری که قبلاً نصب شده، همان دستور نصب را یک بار دیگر اجرا کنید. این کار بی‌خطر است و Xray را اضافه می‌کند. اگر فایل‌های انتشار GitHub روی سرور بسته باشند، Xray از شاخهٔ `xray-core` همین مخزن گرفته می‌شود. هر بار با SHA-256 منتشرشدهٔ خود Xray مقایسه می‌شود.
2. در **پنل سرور ← پروکسی شبکه‌های اجتماعی** لینک سرور خود را وارد کنید و «ذخیره و اجرا» را بزنید. لینک می‌تواند یکی از این‌ها باشد:
   - `vless://` با REALITY یا TLS؛
   - `vmess://`، `trojan://` یا `ss://`؛
   - SOCKS یا HTTP؛
   - JSON خروجی Xray.

   پنل سرور باید روشن باشد: `sudo mobocom panel on --ip YOUR.IP.ADDRESS` (بخش «پنل سرور با یک دستور»).
3. «آزمایش اتصال» را بزنید. باید تلگرام و اینستاگرام هر دو «پاسخ داد» نشان دهند. با دکمهٔ روشن/خاموش می‌توانید ارسال را دوباره مستقیم کنید، بدون اینکه پیکربندی پاک شود.

**امنیت:**
- **فقط محلی:** پروکسی فقط روی `127.0.0.1` گوش می‌دهد و از اینترنت در دسترس نیست. با کاربر محدود خودش و سرویس محافظت‌شده اجرا می‌شود.
- **فقط مقصد مشخص می‌شود:** پنل فقط تعیین می‌کند ترافیک از کجا خارج شود. پورت و مسیرها را ابزار ریشهٔ سرور خودش می‌سازد. فقط دامنه‌های تلگرام و اینستاگرام/فیسبوک از پروکسی عبور می‌کنند و بقیه را Xray مسدود می‌کند.
- **بررسی پیش از اعمال:** پیکربندی‌ای که خود Xray نپذیرد، مثلاً VLESS بدون TLS یا REALITY، جای پیکربندی فعلی را نمی‌گیرد.
- **ذخیره و گزارش:** لینک رمزگذاری‌شده ذخیره می‌شود. در گزارش فعالیت پنل فقط نوع پروتکل و نشانی سرور ثبت می‌شود.

## کلیدها و بررسی نصب

از /etc/mobocom/mobocom.env نسخهٔ امن خارج از سرور نگه دارید. PANEL_CREDENTIAL_KEY، کلید بکاپ و سایر اسرار آن را تغییر ندهید و در Git، تیکت یا پیام‌رسان نفرستید.

فایل /etc/mobocom/release-public.pem فقط کلید عمومی ناشر است. کلید خصوصی امضای انتشار روی سرور سایت قرار نمی‌گیرد و از پنل قابل تعویض نیست. تعویض اعتماد به ناشر اقدام صریح اپراتور است.

    sudo mobocom status

سپس ورود مدیر، ذخیرهٔ نوشته، آپلود تصویر و پیش از فروش واقعی یک خرید آزمایشی را بررسی کنید.

## گزینه‌ها و خطاها

| گزینه یا نشانه | اقدام |
| --- | --- |
| --no-ssl | گواهی نمی‌گیرد؛ HTTPS را از پراکسی یا پس از تنظیم DNS تأمین کنید. کد نصب و رمز روی HTTP عمومی وارد نشود. |
| --no-firewall | دیواره‌آتش فعلی را حفظ می‌کند. حالت عادی ابتدا پورت‌های واقعی SSH را بررسی می‌کند. |
| خطای امضا/ناشر | فایل سالم و ناشر مورد اعتماد را بررسی کنید؛ تأیید امضا را دور نزنید. |
| publisher key differs | اعتماد قبلی حفظ شده؛ تغییر کلید فقط با بررسی اپراتور انجام شود. |
| the site did not start | دستور زیر را بررسی کنید. |
| حافظه/دیسک کم | منابع کافی فراهم و نصب/ساخت را تکرار کنید؛ دادهٔ موجود حذف نشود. |
| گواهی صادر نشد | DNS و پورت موردنیاز روش انتخاب‌شده را اصلاح و همان مرحلهٔ SSL را دوباره اجرا کنید؛ کد یا داده‌ها را پاک نکنید. |

### اگر `/install` خطای ۴۰۴ می‌دهد

تا زمانی که نصب‌کننده پیام `Installed` را نشان نداده، نصب تمام نشده است. پیام `Compiled successfully` فقط پایان کامپایل است؛ بررسی TypeScript و ادامهٔ بیلد، راه‌اندازی سرویس و تنظیم Nginx هنوز باقی است. در این فاصله، پاسخ پیش‌فرض Nginx ممکن است ۴۰۴ باشد.

برای تشخیص بدون نمایش رمزها:

```bash
sudo systemctl is-active mobocom
sudo test -f /opt/mobocom/app/.next/BUILD_ID && echo BUILD_COMPLETE || echo BUILD_INCOMPLETE
curl -sS --max-time 10 -o /dev/null -w 'APP_HTTP=%{http_code}\n' -H 'Host: example.com' http://127.0.0.1:3000/install
```

`example.com` را با دامنهٔ خود عوض کنید. اگر بیلد هنوز اجرا می‌شود، بگذارید تمام شود. اگر متوقف شده، خطای نهایی بیلد را بررسی و پس از رفع علت همان نصب‌کنندهٔ معتبر را دوباره اجرا کنید؛ env، دیتابیس و فایل‌های موجود حفظ می‌شوند. برای سرویس ناموفق، لاگ زیر را روی سرور بررسی کنید؛ پیش از ارسال لاگ، کد خصوصی نصب و هر رمز را حذف کنید.

اگر پاسخ داخلی برنامه ۲۰۰ است ولی دامنه ۴۰۴ Nginx می‌دهد، تنظیم دامنه/پراکسی را با `sudo nginx -t` و فایل `/etc/nginx/sites-enabled/mobocom` بررسی کنید. نصب‌کننده تنظیم سفارشی موجود را بازنویسی نمی‌کند. برای ورود به ویزارد از `https://دامنه/install` استفاده کنید؛ رمز و کد نصب را روی HTTP عمومی وارد نکنید.

اگر خود برنامه در پاسخ داخلی ۴۰۴ می‌دهد، وجود مدیر، `installed.lock` یا `INSTALL_DISABLED=true` می‌تواند به معنی بسته‌بودن عمدی ویزارد باشد؛ از صفحهٔ ورود استفاده کنید. برای بازکردن ویزارد، مدیر یا قفل نصب را حذف نکنید.

    sudo journalctl -u mobocom -n 80 --no-pager

با Cloudflare از Full (strict) و گواهی معتبر تا سرور استفاده کنید. نصب VPS واقعی، فایروال و صدور/تمدید واقعی گواهی باید روی زیرساخت مقصد هم تأیید شوند؛ تست محلی معادل استقرار نیست.

## ساخت بسته برای ناشر

این مرحله برای نگهدارندهٔ پروژه است، نه مدیر سرور:

    node scripts/build-release-package.cjs keygen /secure/offline/mobocom-keys
    node scripts/build-release-package.cjs build /secure/distribution /secure/offline/mobocom-keys/release-private.pem

ناشر به Git محلی و Python نیاز دارد؛ کد از HEAD ثبت‌شده بسته‌بندی می‌شود. خروجی: فایل run، بستهٔ mbrelease، کلید عمومی و checksum. فایل‌های کاربران، env، Git، ابزار ایجنت، node_modules و کلیدهای خصوصی داخل انتشار نیستند. کلید امضا را یک بار بسازید و برای نسخه‌های بعدی همان کلید را با نسخهٔ جدید package.json نگه دارید. از کلید خصوصی جداگانه پشتیبان بگیرید؛ آن را به هاست دانلود منتقل نکنید.
