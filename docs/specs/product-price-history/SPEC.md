# Product price history — implementation slice

## Evidence and outcome
Price history/alerts are absent from both Prisma schemas and Store/Catalog services. Existing exact minor-unit prices and unitPrice remain authoritative. Price writes exist in CMS, Marketplace full/quick updates, Store bulk-price edits, Import's product/variant transaction and FX repricing/conversion. Stock/view/description writes must not generate price changes. Extend these owners through one Catalog pricing-capture contract; avoid a separate pricing engine.

## Planned contract
- Add an incremental ProductPricePoint table in both Prisma schemas plus PostgreSQL migration; retain existing Product/ProductVariant/Order records. Point fields: productId, variantId (0 = base product), amountMinor, currency, recordedAt and ID; index product/variant/time. No human identity copy. Record observations of regular public prices, excluding VIP/list prices, draft/private prices and buyer data.
- One typed capture service runs inside each successful pricing transaction. Serialize capture per product in PostgreSQL using the same product-row lock before product/variant price writes, then compare with the last recorded price for each live variant/base; append only changed positive amount/currency points. Creation/approval/reactivation can establish a public baseline. Metadata/stock edits with unchanged recorded price append nothing. Rollback removes all associated points; concurrent/idempotent saves must not create duplicate observations.
- Prepare a bounded, restartable baseline job for current public products; observations start at capture time and must not fabricate earlier history. Existing historical prices cannot be recovered from current rows. Review Import undo and FX transaction semantics before adding hooks.
- Existing Store merchandising settings own showPriceHistory (safe rollout default false) and bounded priceHistoryDays (30–730, default 365), preserving omitted keys for old clients. Disabling public history preserves captured data. Keep public read horizon configurable; defer destructive retention until a separate verified retention policy.
- Extend the existing product-tab API additively with price-history. Store/publication/setting gates apply; validate selected active variant ownership. Read only that product/variant and current currency, at most 120 recent points in the configured horizon, ascending chronological display with explicit truncation; never expose pending/unapproved prices or mix currencies. Document the API contract and an empty/partial-history explanation.
- Add a tab using the existing ProductTabs composition/tokens; show an accessible trend and exact formatted values, loading/empty/error states, proper RTL/LTR and dark/light/mobile behavior. Preserve existing tabs, variant selection, buy box, cart and all protected site surfaces.

## Acceptance and migration safety
Check unchanged price, price/currency delta, base/variant ownership, private/public transitions, stock/metadata no-op, creation, rollback, concurrent capture, all six price writers including Import undo and FX, baseline checkpoints/retry, invalid/disabled/unapproved public reads and bounded output. Use unit/service checks, real PostgreSQL/API and relevant browser/a11y checks, schema parity/migration status, TypeScript/source/architecture/security, contract lint and clean-source build. Apply only the additive migration to local Docker for verification; production backup/preflight/migration/deployment remain unverified until actual deployment access exists. Price-drop subscriptions/notifications/bundles are later slices through central Identity/Notifications/Jobs, not part of this slice's completion claim.
