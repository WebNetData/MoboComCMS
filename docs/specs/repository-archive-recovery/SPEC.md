# Repository archive recovery through existing owners

## Target and safety dependency

Continue foundation32 d021862. Current rollback compensation preserves archives during database uncertainty, but process termination bypasses catch. Existing integrity CLI has no filesystem findings, and no separate archive recovery owner exists. Extend Repository vendor/Admin, the existing integrity report and existing lifecycle/settings/audit services; preserve paths, receipts, licenses, schema compatibility and approved UI.

Recovery means discovering, reviewing and safely resolving retained archives without deleting referenced releases or racing in-flight uploads. Age alone cannot fence a paused uploader. Destructive automatic cleanup is not authorized by a scan finding. Before mutation controls, provide durable upload reservation/phase fencing through the existing release owner, with an incremental migration/default preserving current rows and all public queries; recheck the phase at finalization. A recovery operation claims reviewed evidence and current actor/module, records the action through the existing audit owner, and preserves rollback/unknown outcomes. No parallel job/auth/settings system or arbitrary paths. Quarantine/restore remains reversible; crash recovery and restart behavior must have actual evidence before certification.

## Coherent implementation order

1. Connect read-only diagnosis to the existing integrity CLI and vendor Admin API. Stream flat directory names with bounded retained memory, deterministic filename pagination; release rows use ID pagination. Only valid repository archive filenames are inspected. Reject symlink directories; refuse symlink/nonregular/oversized files and traversal. Compare sizes and optionally stream checksums; detect replacement while inspected. Report scan caps/cursors/observed coverage explicitly and never print content/keys/email. Default existing CLI findings remain unchanged; filesystem inspection is explicit and local, using the deployed archive directory. No writes/audit or cloud analysis during diagnosis.
2. Add data-safe reservation/phase fencing to existing upload/release lifecycle before any recovery mutation. Prove old rows/public URLs/queries, actual concurrent finalization/recovery, actor/module transitions, original audit semantics and rollback. Configure legitimate operational settings in the existing vendor Control Plane.
3. Add reviewed quarantine/restore/resume controls through the same Repository Admin and canonical audit/jobs owners; actual crash/restart and unavailable-storage tests. Add UI using existing tokens/SDS, Doctor and actual themed/mobile/keyboard/axe checks. Existing public machine/provider and package application gaps remain part of the whole roadmap.

For slice1 use the same actual source inspector in CLI and application. Connected PostgreSQL + real temporary archive files, read-only database proxy, missing/healthy/unreferenced/shared/unsafe/symlink/size/hash/replacement/cursor cases, explicit opt-in compatibility, current Admin permission/module and unchanged snapshots; deliberate faults and relevant general/compiled tests. A read-only slice never certifies recovery mutations or overall production readiness.
