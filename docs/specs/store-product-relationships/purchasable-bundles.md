# Purchasable product bundles

## Audit / outcome
Catalog owns Product/ProductVariant and CMS writes; Store owns the only Cart/CartLine, unitPrice and cart checkout. Checkout snapshots each component into canonical OrderLine, and existing Inventory reserves every line atomically. No purchasable bundle model/service exists. Editorial relationships and co-purchase suggestions are separate capabilities. A bundle is a named fixed selection of actual products/variants/quantities that can be added together to the existing cart.

## Ownership / actors / data
Catalog owns ordered ProductBundle definitions attached to an existing source Product and ordered components. Admin `cms.products` edits only bundles owned by that product, through its existing transaction/price lock. Up to eight definitions per product, two to twelve unique product/variant components, quantity1–30, bounded plain text name/nameEn. The source must itself be a component; a variant-bearing product must have an explicit active variant. Editing preserves retained withdrawn references; new choices must currently be public. Target deletion keeps the component as unavailable (nullable FK) rather than silently selling an incomplete bundle. Source deletion cascades only its bundle definitions. Creation of bundle definitions starts in an existing product editor after the product exists; legacy product writers that omit bundles preserve them.

## Happy / failure path
Store default-off Admin rollout controls display and adding. Public source detail displays active complete public bundles, component variants/quantities and current existing per-line prices with their summed total. No separate bundle discount is promised in this first slice. Member prices/access use canonical membership. Buy adds all fixed components atomically to the existing owner cart; unavailable variant/source/target, membership restriction, stock or per-order cap, mixed currency and full cart reject the whole operation, retaining prior cart lines/cycle. No partial clamping for a bundle. Component stock is not reserved by adding to cart; checkout still reprices and reserves through existing services. Normal cart lines remain independently editable with explicit UI copy; no duplicate order/inventory/refund path or new identity.

## Contracts / UI / migration
Additive CMS optional bundles field, scoped public product bundle read and POST `/api/cart` bundleId alternative to legacy productId. Reject ambiguous single-product/bundle payloads. Preserve existing response cart/limited fields, cookie/owner checks, URLs, permissions and old clients. Hidden/missing source or Store/rollout off returns no bundle data; definitions persist. Admin editor reuses current card/input/picker primitives; public component uses current Store layout/tokens, Persian/English copy, RTL and light/dark/responsive checks. PostgreSQL additive tables/indexes/FKs plus matching SQLite model; snapshot local DB, apply real migration, no destructive data update.

## Acceptance

Actual Admin search/variant/quantity/edit/save/reload and product/cart browser flow; rollout/withdrawal and public API contracts Hurl/Spectral. TypeScript/source/security/architecture/cruiser, relevant suites and clean committed-source build/CI before merge. External payment delivery and production backup/restore/deploy are separate verification. Bundle-specific discounts and refund allocation require a future explicit pricing spec.
