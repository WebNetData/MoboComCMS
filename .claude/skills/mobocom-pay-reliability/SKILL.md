# MoboCom Pay Reliability

## Mission
Ship evidence-backed, end-to-end payment changes without breaking supported existing behavior. Do not claim zero defects or production readiness without evidence. This skill complements mobocom-premium-design; payment integrity takes precedence over visual polish.

## Workflow
1. Start with [architecture](../../../docs/agent/ARCHITECTURE.md), [payment quality gates](../../../docs/agent/ENGINEERING_SKILLS.md#payment-quality-gates) and the [Pay handoff](../../../docs/agent/handoffs/MOBOCOM_PAY.md). Read applicable AGENTS.md and the relevant payment contracts, schema, migrations, UI, API, jobs and test commands. Inspect current worktree; preserve unrelated user changes. Identify actual dependencies and existing capabilities before proposing new ones.
2. Reproduce reported issues in a local or isolated staging environment using synthetic data. Capture sanitized error, request/response, state and root cause. Run relevant baseline tests and distinguish pre-existing failures from new failures. Never test destructive operations on production or send real money without separately authorized controls.
3. Define acceptance criteria and affected invariants. Add a failing regression test for each reproducible bug before fixing where practical; document any inability to reproduce or test. Consult the [regression matrix](references/regression-matrix.md) for existing executable coverage and acceptance gaps.
4. Make the smallest coherent end-to-end change (UI, server validation, authorization, persistence, worker/cache synchronization as needed). Avoid unrelated rewrites, duplicate sources of truth and breaking API contracts. Use the project's existing stack. Document schema/API changes, migration strategy and rollback/recovery, including irreversible effects; do not apply production migrations or deploy automatically.
5. Run relevant unit, integration (real isolated DB), concurrency, API authorization, and browser E2E tests. Run the affected repository checks and regressions. For a payment release, also run the full connected Pay suite and historical upgrade gate. Never weaken assertions, silently skip tests, mock away the failing integration, or mark unexecuted checks as passed.
6. Review the diff independently from implementation (separate review pass/agent when available), focusing on tenant isolation, trust boundaries, payment correctness, migration safety, race conditions and UI/API parity. Fix findings and rerun affected checks.
7. Report root causes, changed files, migrations, tests with exact commands/results, evidence, pre-existing failures, remaining risks, and release blockers. A successful build alone is not acceptance. Do not deploy; hand off for authorized release.

## Domain invariants
- Determine existing entities/relationships for bank accounts, cards, auto-verification configuration, forwarding sources, terminals, gateway assignments, payment intents, events and records. Do not create parallel models if existing models can be evolved.
- Separate receiving-method status, verification capability and per-terminal assignment/eligibility. Derive eligibility server-side from a single authoritative policy shared by checkout and admin APIs. Provide an authorized management UI to view, assign, unassign and diagnose ineligible methods; enforce tenant ownership and eligibility at the API, not only in the UI.
- Model account/card disable, archive and delete explicitly. Historical financial records and auditability must survive. Do not blindly cascade, drop constraints or orphan references. For pending obligations, block with an actionable reason or use a documented drain/disable lifecycle. Preserve reconciliation of in-flight payments. Removal of one method must not disrupt unrelated methods. Make state transitions consistent across worker, cache and UI; use transactions and reliable post-commit effects where applicable.
- Treat money as integer minor units or an existing exact decimal representation; verify currency/unit conversions explicitly (including toman/rial if applicable). Allocate unique payable amounts atomically within the real matching scope, with expiry and collision handling; enforce database invariants where supported. Never match only on amount if receiver/source identity or other necessary evidence is absent or ambiguous. Handle late events, reuse windows and ambiguous matches conservatively.
- SMS is an untrusted payment signal, not independent bank settlement proof. Authenticate forwarding ingress, bind each source to authorized receiving accounts, validate parsed events and prevent replay; a claimed sender name alone is insufficient. Prefer authoritative bank/provider reconciliation when available. Quarantine ambiguous, suspicious, late or unmatched events for authorized review rather than auto-crediting. If required trust or receiver identity cannot be established, fail closed and report blocker.
- Make event ingestion and payment finalization idempotent; a duplicated or concurrently delivered event cannot confirm multiple payments or generate duplicate balance/ledger entries or callbacks. Enforce atomic conditional state transitions and uniqueness using the actual DB; persist delivery/outbox state if callbacks exist and use retry-safe delivery. Do not assume exactly-once network delivery.
- Preserve transaction history and audit actor, action, reason, timestamp and correlation IDs. Mask card/account data; never log secrets, full sensitive SMS text, or unnecessary personal data. Use least privilege, tenant-scoped checks, rate limits, secure secret management and existing security controls.
- Keep UI states truthful: enabled, disabled, unavailable, pending, error and success must correspond to actual server state. Apply [mobocom-premium-design](../mobocom-premium-design/SKILL.md) to every affected payment UI. Its SDS and Unslop routing governs presentation, RTL, localization and accessibility.

## Release gate
Block payment merge and release while required payment tests fail, high or critical payment-integrity or security issues remain, or critical evidence is missing. Record limitations and route for human review. Do not claim full settlement verification from SMS alone. No real funds, production data changes, destructive migrations, external callbacks or deployment without separate authorization.
